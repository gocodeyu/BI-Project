### 1.2 技术选型对比

```
┌─────────────────────────────────────────────────────────┐
│                    技术选型决策树                          │
└─────────────────────────────────────────────────────────┘

异步处理？
├─ 是 → 使用什么？
│      ├─ 简单场景 → 线程池 ThreadPoolExecutor
│      └─ 复杂场景 → 消息队列 RabbitMQ ✅
│                   （解耦、削峰、可靠性、扩展性）
│
缓存方案？
├─ 单机 → Caffeine（本地缓存）
├─ 分布式 → Redis（分布式缓存）✅
└─ 多级 → Caffeine + Redis ✅
           （热点数据本地缓存，降低Redis压力）

分布式锁？
├─ 基于数据库 → 悲观锁/乐观锁
├─ 基于Redis → Redisson ✅
│              （高性能、功能丰富、自动续期）
└─ 基于Zookeeper → Curator
                   （强一致性，但性能较低）

限流方案？
├─ 单机限流 → Guava RateLimiter
└─ 分布式限流 → Redisson RRateLimiter ✅
                （分布式环境、支持多种算法）
```

### 3.3 重试策略图

```
┌────────────────────────────────────────────────────────────┐
│                    Spring AMQP 重试策略                      │
└────────────────────────────────────────────────────────────┘

第1次失败
    │
    ├─ 等待 2秒 (initial-interval)
    │
    ▼
第2次尝试
    │
    ├─ 失败 → 等待 4秒 (2 * multiplier)
    │
    ▼
第3次尝试
    │
    ├─ 失败 → 等待 8秒 (4 * multiplier)
    │
    ▼
第4次尝试 (max-attempts = 3 + 1)
    │
    ├─ 仍失败 → 进入死信队列
    │
    ▼
┌──────────────────────────────────────┐
│      Dead Letter Queue               │
│  - 人工查看日志                       │
│  - 分析失败原因                       │
│  - 手动重新提交或标记为失败           │
└──────────────────────────────────────┘

配置参数：
- max-attempts: 3 (最多重试3次)
- initial-interval: 2000ms (初始间隔2秒)
- multiplier: 2 (间隔倍增)
- max-interval: 10000ms (最大间隔10秒)
```

### 4.2 缓存Key设计

   ┌──────────────────────────────────────────┐

   │ TTL: 15分钟 ± 60秒随机偏移               │

   │   - genResult: "..."                     │
   │   - status: "succeed"                    │
   └──────────────────────────────────────────┘

2. 图表列表缓存（Caffeine + Redis）
   ┌──────────────────────────────────────────┐
   │ Redis Key:                               │
   │ bi:chart:list:my:{userId}:p{page}:       │
   │                  s{pageSize}:v{version}  │
   │ Type: String (JSON)                      │
   │ TTL: 60秒                                │
   │ 示例: bi:chart:list:my:123:p1:s10:v5     │
   │                                          │
   │ Caffeine Key:                            │
   │ chart:list:my:{userId}:p{page}:          │
   │              s{pageSize}:v{version}      │
   │ TTL: 20秒                                │
   │                                          │
   │ 版本号Key:                                │
   │ bi:chart:list:my:{userId}:v              │
   │ Type: String                             │
   │ TTL: 7天                                 │
   │ 示例: bi:chart:list:my:123:v → "5"       │
   └──────────────────────────────────────────┘

3. 数据预览缓存（Caffeine + Redis）

### 4.3 版本号机制

```
┌────────────────────────────────────────────────────────────┐
│                  版本号机制（解决列表缓存删除难题）          │
└────────────────────────────────────────────────────────────┘

传统方案（删除所有分页缓存）：
┌──────────────────────────────────────┐
│ 新增图表                              │
│   ↓                                  │
│ 需要删除：                            │
│   - list:my:123:p1:s10               │
│   - list:my:123:p2:s10               │
│   - list:my:123:p3:s10               │
│   - list:my:123:p1:s20               │
│   - list:my:123:p2:s20               │
│   - ...（很多Key）                    │
│                                      │
│ 问题：                                │
│ 1. 需要遍历删除，性能差               │
│ 2. 可能遗漏某些Key                    │
│ 3. 并发情况下可能出现脏数据           │
└──────────────────────────────────────┘

版本号方案（递增版本号）：
┌──────────────────────────────────────┐
│ 初始状态：                            │
│   version = 1                        │
│   缓存Key: list:my:123:p1:s10:v1     │
│                                      │
│ 新增图表：                            │
│   version++ → 2                      │
│   新缓存Key: list:my:123:p1:s10:v2   │
│                                      │
│ 旧缓存自动失效：                      │
│   list:my:123:p1:s10:v1 (过期)       │
│                                      │
│ 优点：                                │
│ 1. 只需递增一个数字，O(1)操作        │
│ 2. 不会遗漏                           │
│ 3. 并发安全                           │
└──────────────────────────────────────┘

实现代码：
┌──────────────────────────────────────┐
│ // 查询时                             │
│ String versionKey =                  │
│   "bi:chart:list:my:" + userId + ":v"│
│ Long version = redis.get(versionKey) │
│ String cacheKey =                    │
│   "list:my:" + userId + ":p" + page  │
│   + ":s" + size + ":v" + version     │
│                                      │
│ // 删除缓存时                         │
│ redis.increment(versionKey)          │
│ // 旧缓存自动失效，无需手动删除       │
└──────────────────────────────────────┘
```

## 总结

### 核心流程图总结

1. **新建图表分析**：参数校验 → 限流 → 分布式锁 → 保存DB → 发送MQ → 异步处理
2. **异步化处理**：RabbitMQ队列 → Consumer消费 → AI调用 → 更新DB → SSE通知

5. **限流策略**：频率限流 + 每日限流 + 限流回退，令牌桶算法
