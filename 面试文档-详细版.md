## 1. 项目背景

### 1.1 业务场景

用户上传Excel数据文件，系统自动调用AI（如通义千问）进行数据分析，生成可视化图表和分析结论。

### 1.2 技术挑战

1. **AI调用耗时长**：单次分析需10-30秒，同步调用会阻塞用户
2. **高并发访问**：多用户同时查询图表列表，数据库压力大
3. **重复提交**：用户手抖或网络延迟导致重复提交，浪费AI Token
4. **资源滥用**：恶意用户频繁调用接口，消耗系统资源

### 1.3 技术选型

| 技术 | 版本 | 用途 |
|------|------|------|
| Spring Boot | 2.7.x | 基础框架 |
| MyBatis-Plus | 3.5.x | ORM框架 |
| Redis | 7.0 | 分布式缓存 |
| Redisson | 3.20.x | 分布式锁 + 限流 |
| Caffeine | 3.1.x | 本地缓存 |
| RabbitMQ | 3.12.x | 消息队列 |
| AI SDK | - | 通义千问API |

## 3. 异步化处理详解

### 3.1 为什么需要异步化？

**同步调用的问题**：
```java
// 同步方式（不推荐）
String result = aiManager.doChat(prompt); // 阻塞10-30秒
// 用户需要等待，体验差
// Tomcat线程被占用，并发能力低
```

**异步化的优势**：
- 用户立即得到响应，体验好
- Tomcat线程快速释放，并发能力高
- 任务可以削峰填谷，系统更稳定

### 3.2 RabbitMQ配置

#### 队列设计

```java
@Configuration
public class RabbitMqConfig {
    // 交换机
    public static final String BI_EXCHANGE_NAME = "bi_exchange";
    
    // 业务队列
    public static final String BI_VIP_QUEUE_NAME = "bi_vip_queue";
    public static final String BI_COMMON_QUEUE_NAME = "bi_common_queue";
    
    // 死信队列
    public static final String BI_DLX_EXCHANGE_NAME = "bi_dlx_exchange";
    public static final String BI_DL_QUEUE_NAME = "bi_dl_queue";
    
    // VIP队列配置（绑定死信交换机）
    @Bean
    public Queue biVipQueue() {
        Map<String, Object> args = new HashMap<>();
        args.put("x-dead-letter-exchange", BI_DLX_EXCHANGE_NAME);
        args.put("x-dead-letter-routing-key", BI_DL_ROUTING_KEY);
        return QueueBuilder.durable(BI_VIP_QUEUE_NAME)
                .withArguments(args).build();
    }
}
```

**设计要点**：
1. **VIP队列 vs 普通队列**：VIP用户优先处理
2. **死信队列**：处理失败的消息不丢失
3. **持久化**：队列和消息都持久化到磁盘

### 3.3 生产者实现

```java
@Component
public class BiMessageProducer {

        rabbitTemplate.convertAndSend(
            RabbitMqConfig.BI_EXCHANGE_NAME,
            routingKey,
            message
        );
        
        log.info("发送消息到{}队列: {}", isVip ? "VIP" : "普通", message);
    }
}
```

### 3.4 消费者实现

```java
@Component
@Slf4j
public class BiMessageConsumer {
    @Resource
    private BiAsyncService biAsyncService;
    
    /**
     * VIP队列消费者（5-10个并发）
     */
    @RabbitListener(
        queues = RabbitMqConfig.BI_VIP_QUEUE_NAME, 
        concurrency = "5-10",
        ackMode = "MANUAL"
    )
    public void receiveVipMessage(
        String message, 
        Channel channel, 
        @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag
    ) throws IOException {
        try {
            log.info("VIP消费者收到消息: {}", message);
            
            // 执行业务逻辑
            biAsyncService.executeGenChart(Long.parseLong(message));
            
            // 手动ACK
            channel.basicAck(deliveryTag, false);
            
        } catch (RetryableException e) {
            // 可重试异常：抛出让Spring自动重试
            log.warn("VIP队列可重试异常: {}", e.getMessage());
            throw e;
            
        } catch (Exception e) {
            // 不可重试异常：拒绝消息，进入死信队列
            log.error("VIP队列不可重试异常: {}", e.getMessage(), e);
            channel.basicNack(deliveryTag, false, false);
        }
    }
}
```

**关键配置**：
- `concurrency = "5-10"`：动态调整消费者数量
- `ackMode = "MANUAL"`：手动ACK，更精准控制
- **异常分类**：可重试 vs 不可重试

### 3.5 重试机制

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual
        retry:
          enabled: true
          max-attempts: 3        # 最多重试3次
          initial-interval: 2000ms  # 初始间隔2秒
          multiplier: 2          # 间隔倍增
          max-interval: 10000ms  # 最大间隔10秒
```

**重试策略**：
- 第1次失败：等待2秒后重试
- 第2次失败：等待4秒后重试
- 第3次失败：等待8秒后重试
- 仍失败：进入死信队列

### 3.6 异步业务逻辑

```java
@Service
public class BiAsyncServiceImpl implements BiAsyncService {
    @Resource
    private ChartService chartService;
    @Resource
    private AiPrompt aiPrompt;
    @Resource
    private SseNotifyService sseNotifyService;
    
    // AI专用线程池
    private final ThreadPoolExecutor aiExecutor = new ThreadPoolExecutor(
        2, 4, 60L, TimeUnit.SECONDS, 
        new LinkedBlockingQueue<>(10)
    );
    
    @Override
    public void executeGenChart(long chartId) {
        // 1. 更新状态为"执行中"
        Chart updateChart = new Chart();
        updateChart.setId(chartId);
        updateChart.setStatus(GenChartStatusEnum.RUNNING.getValue());
        chartService.updateById(updateChart);
        
        try {
            // 2. 查询数据
            Chart chart = chartService.getById(chartId);
            String tableName = "chart_" + chartId;
            List<Map<String, Object>> data = chartMapper.queryChartData(tableName);
            String csvData = ExcelUtils.mapToString(data);
            
            // 3. 构造重试器（Guava Retrying）
            Retryer<String> retryer = RetryerBuilder.<String>newBuilder()
                .retryIfException()
                .withWaitStrategy(WaitStrategies.fixedWait(2, TimeUnit.SECONDS))
                .withStopStrategy(StopStrategies.stopAfterAttempt(3))
                .build();
            
            // 4. 调用AI（带超时控制）
            String result = CompletableFuture.supplyAsync(() -> {
                try {
                    return retryer.call(() -> 
                        aiPrompt.func(chart.getGoal(), chart.getChartType(), csvData)
                    );
                } catch (Exception e) {
                    throw new RuntimeException("AI生成失败: " + e.getMessage());
                }
            }, aiExecutor).get(2, TimeUnit.MINUTES);
            
            // 5. 解析结果
            String[] splits = result.split("【【【【【");
            String genChart = splits[1].trim();
            String genResult = splits[2].trim();
            
            // 6. 更新数据库为成功
            Chart updateSuccess = new Chart();
            updateSuccess.setId(chartId);
            updateSuccess.setGenChart(genChart);
            updateSuccess.setGenResult(genResult);
            updateSuccess.setStatus(GenChartStatusEnum.SUCCEED.getValue());
            chartService.updateById(updateSuccess);
            
            // 7. 删除缓存
            evictChartCache(chartId, chart.getUserId());
            
            // 8. SSE通知前端
            sseNotifyService.publishTaskNotification(
                chart.getUserId(), chartId, "succeed", "图表生成成功"
            );
            
        } catch (TimeoutException e) {
            log.error("AI生成超时: chartId={}", chartId);
            handleChartUpdateError(chartId, "AI生成超时");
        } catch (Exception e) {
            log.error("AI生成失败: chartId={}", chartId, e);
            handleChartUpdateError(chartId, "执行失败: " + e.getMessage());
        }
    }
}
```

**核心要点**：
1. **状态管理**：WAIT → RUNNING → SUCCEED/FAILED
2. **重试机制**：Guava Retrying，最多3次
3. **超时控制**：CompletableFuture.get(2分钟)
4. **缓存删除**：成功后立即删除缓存
5. **SSE通知**：实时推送结果给前端

## 4. 多级缓存详解

### 4.1 缓存架构设计

```
请求流程：
Controller → Caffeine → Redis → MySQL
             ↑(20s)    ↑(15min)  ↑(永久)
```

**三级缓存对比**：

| 缓存层级 | 存储位置 | 容量 | 速度 | TTL | 适用场景 |
|---------|---------|------|------|-----|---------|
| Caffeine | JVM内存 | 1000条 | 最快（ns级） | 20秒 | 热点数据 |
| Redis | 独立进程 | 10GB | 快（ms级） | 15分钟 | 分布式共享 |
| MySQL | 磁盘 | 无限 | 慢（10ms+） | 永久 | 持久化存储 |

### 4.2 图表详情缓存（Redis + DB）

**为什么不用Caffeine？**
- AI分析完成后通过SSE推送通知
- Caffeine是本地缓存，多节点数据不一致
- Redis是集中式缓存，更新后所有节点可见

```java
@Service
public class ChartCacheService {
    private static final String REDIS_KEY_PREFIX = "bi:chart:";
    private static final int TTL_MINUTES = 15;
    private static final int TTL_RANDOM_OFFSET_SECONDS = 60;
    
    @Resource
    private StringRedisTemplate stringRedisTemplate;
    @Resource
    private ChartService chartService;
    
    /**
     * 获取图表详情（Redis + DB）
     */
    public Chart getChartByIdWithCache(Long chartId) {
        if (chartId == null || chartId <= 0) {
            return null;
        }
        
        String redisKey = REDIS_KEY_PREFIX + chartId;
        
        try {
            // 1. 查Redis（Hash结构）
            Map<Object, Object> entries = stringRedisTemplate
                .opsForHash().entries(redisKey);
            
            if (!entries.isEmpty()) {
                log.debug("Redis缓存命中: chartId={}", chartId);
                return mapToChart(entries);
            }
            
            // 2. 查数据库
            Chart chart = chartService.getById(chartId);
            if (chart == null) {
                return null;
            }
            
            // 3. 写入Redis（TTL + 随机偏移）
            int ttl = TTL_MINUTES * 60 + 
                     ThreadLocalRandom.current().nextInt(-TTL_RANDOM_OFFSET_SECONDS, 
                                                         TTL_RANDOM_OFFSET_SECONDS);
            
            stringRedisTemplate.opsForHash().putAll(redisKey, chartToMap(chart));
            stringRedisTemplate.expire(redisKey, ttl, TimeUnit.SECONDS);
            
            log.debug("查询数据库并缓存: chartId={}", chartId);
            return chart;
            
        } catch (Exception e) {
            log.error("缓存查询失败，降级到数据库: chartId={}", chartId, e);
            return chartService.getById(chartId);
        }
    }
    
    /**
     * 删除缓存
     */
    public void evictChart(Long chartId) {
        if (chartId != null && chartId > 0) {
            String redisKey = REDIS_KEY_PREFIX + chartId;
            stringRedisTemplate.delete(redisKey);
            log.debug("删除缓存: chartId={}", chartId);
        }
    }
}
```

**设计要点**：
1. **Hash结构**：比String更省内存，支持部分字段更新
2. **随机TTL**：避免缓存雪崩（大量缓存同时过期）
3. **降级策略**：Redis异常时直接查DB
4. **主动删除**：更新数据后立即删除缓存

### 4.3 图表列表缓存（Caffeine + Redis + DB）

**版本号机制**：
- 传统方案：删除缓存很麻烦（需要遍历所有分页）
- 版本号方案：递增版本号，旧缓存自动失效

```java
@Service
public class ChartListCacheService {
    private static final String REDIS_VERSION_KEY_PREFIX = "bi:chart:list:my:";
    private static final String REDIS_DATA_KEY_PREFIX = "bi:chart:list:my:";
    private static final String CAFFEINE_KEY_PREFIX = "chart:list:my:";
    
    private static final int REDIS_DATA_TTL_SECONDS = 60;
    private static final int CAFFEINE_TTL_SECONDS = 20;
    
    @Resource
    private StringRedisTemplate stringRedisTemplate;
    @Resource
    private ChartService chartService;
    
    // Caffeine本地缓存
    private Cache<String, Page<ChartListVO>> caffeineCache;
    
    @PostConstruct
    public void init() {
        caffeineCache = Caffeine.newBuilder()
            .maximumSize(1000)
            .expireAfterWrite(CAFFEINE_TTL_SECONDS, TimeUnit.SECONDS)
            .build();
    }
    
    /**
     * 获取我的图表列表（三级缓存）
     */
    public Page<ChartListVO> getMyChartListWithCache(ChartQueryRequest request) {
        // 判断是否应该使用缓存（复杂查询不缓存）
        if (!shouldUseCache(request)) {
            return queryFromDb(request);
        }
        
        Long userId = request.getUserId();
        long current = request.getCurrent();
        long pageSize = request.getPageSize();
        
        try {
            // 1. 获取版本号
            String versionKey = REDIS_VERSION_KEY_PREFIX + userId + ":v";
            String versionStr = stringRedisTemplate.opsForValue().get(versionKey);
            Long version = (versionStr == null) ? 1L : Long.parseLong(versionStr);
            
            // 2. 构造缓存Key（包含版本号）
            String cacheKey = REDIS_DATA_KEY_PREFIX + userId + 
                            ":p" + current + ":s" + pageSize + ":v" + version;
            String caffeineKey = CAFFEINE_KEY_PREFIX + userId + 
                               ":p" + current + ":s" + pageSize + ":v" + version;
            
            // 3. 查Caffeine
            Page<ChartListVO> result = caffeineCache.getIfPresent(caffeineKey);
            if (result != null) {
                log.debug("Caffeine缓存命中: userId={}", userId);
                return result;
            }
            
            // 4. 查Redis
            String redisValue = stringRedisTemplate.opsForValue().get(cacheKey);
            if (StringUtils.isNotBlank(redisValue)) {
                log.debug("Redis缓存命中: userId={}", userId);
                result = gson.fromJson(redisValue, 
                    new TypeToken<Page<ChartListVO>>(){}.getType());
                
                // 回写Caffeine
                caffeineCache.put(caffeineKey, result);
                return result;
            }
            
            // 5. 查数据库
            result = queryFromDb(request);
            
            // 6. 写入Redis
            stringRedisTemplate.opsForValue().set(
                cacheKey, 
                gson.toJson(result), 
                REDIS_DATA_TTL_SECONDS, 
                TimeUnit.SECONDS
            );
            
            // 7. 写入Caffeine
            caffeineCache.put(caffeineKey, result);
            
            log.debug("查询数据库并缓存: userId={}", userId);
            return result;
            
        } catch (Exception e) {
            log.error("缓存查询失败，降级到数据库: userId={}", userId, e);
            return queryFromDb(request);
        }
    }
    
    /**
     * 删除缓存（版本号机制）
     */
    public void evictMyChartList(Long userId) {
        if (userId != null && userId > 0) {
            String versionKey = REDIS_VERSION_KEY_PREFIX + userId + ":v";
            // 递增版本号，旧缓存自动失效
            stringRedisTemplate.opsForValue().increment(versionKey);
            log.debug("递增版本号: userId={}", userId);
        }
    }
    
    /**
     * 判断是否应该使用缓存
     */
    private boolean shouldUseCache(ChartQueryRequest request) {
        // 只缓存简单查询：name为空、chartType为空、前3页
        return StringUtils.isBlank(request.getName()) &&
               StringUtils.isBlank(request.getChartType()) &&
               request.getCurrent() <= 3;
    }
}
```

**设计要点**：
1. **版本号机制**：删除缓存只需递增版本号
2. **选择性缓存**：只缓存简单查询和前3页
3. **Caffeine回写**：Redis命中后回写Caffeine
4. **降级策略**：任何异常都降级到DB

### 4.4 数据预览缓存（Caffeine + Redis + DB）

```java
@Service
public class ChartDataCacheService {
    private static final String REDIS_KEY_PREFIX = "bi:chart:data:";
    private static final int REDIS_TTL_SECONDS = 600;  // 10分钟
    private static final int CAFFEINE_TTL_SECONDS = 120; // 2分钟

     */
    public ChartDataPreviewResponse getChartDataPreviewWithCache(
        Long chartId, long current, long pageSize
    ) {
        // 只缓存前3页和常用pageSize
        if (!shouldUseCache(current, pageSize)) {
            return queryFromDb(chartId, current, pageSize);

        // 缓存逻辑同上...
    }

        if (current > MAX_CACHE_PAGE) {
            return false;

                return true;
            }
        }
        return false;
    }
}
```

1. **选择性缓存**：只缓存前3页和常用pageSize（10、20）
2. **较长TTL**：数据预览变化少，可以缓存更久

### 4.5 缓存一致性保证

**Cache Aside模式**：
```java
// 写操作
public void updateChart(Chart chart) {
    // 1. 先更新数据库
    chartService.updateById(chart);
    
    // 2. 再删除缓存
    evictChartCache(chart.getId(), chart.getUserId());
}

// 读操作
public Chart getChart(Long id) {
    // 1. 先查缓存
    Chart chart = getFromCache(id);
    if (chart != null) {
        return chart;
    }
    
    // 2. 缓存未命中，查数据库
    chart = chartService.getById(id);
    
    // 3. 写入缓存
    putToCache(id, chart);
    return chart;
}
```

**一致性策略**：
1. **先更新DB，再删除缓存**：避免脏数据
2. **版本号机制**：列表缓存用版本号
3. **TTL兜底**：所有缓存都有过期时间
4. **随机偏移**：避免缓存雪崩

## 5. 分布式锁详解

### 5.1 为什么需要分布式锁？

**场景**：用户手抖连续点击两次提交按钮

**问题**：
- 产生两条完全相同的AI分析任务
- 浪费AI Token成本（每次0.1-1元）
- 浪费服务器资源

**解决方案**：分布式锁

### 5.2 锁的Key设计

**核心思想**：基于业务特征生成唯一标识

```java
// 新建图表
String lockKey = "chart:gen:" + userId + ":" + 
                 md5(fileContent + goal + chartType);

// 编辑图表
String lockKey = "chart:edit:" + userId + ":" + 
                 md5(chartId + goal + chartType);

// 重试图表
String lockKey = "chart:retry:" + userId + ":" + chartId;
```

**设计要点**：
1. **包含userId**：不同用户可以并发提交相同内容

### 5.3 分布式锁服务实现

```java
@Service
public class DistributedLockServiceImpl implements DistributedLockService {
    @Resource
    private RedissonClient redissonClient;
    
    @Override
    public <T> T executeWithLock(
        String lockKey, 
        long waitTime, 
        long leaseTime, 
        Supplier<T> supplier
    ) throws Exception {
        RLock lock = redissonClient.getLock(lockKey);
        boolean acquired = false;
        
        try {
            // 尝试获取锁
            acquired = lock.tryLock(waitTime, leaseTime, TimeUnit.SECONDS);
            
            if (!acquired) {
                log.warn("获取分布式锁失败，检测到重复提交: lockKey={}", lockKey);
                throw new BusinessException(ErrorCode.OPERATION_ERROR, 
                    "检测到重复提交，请勿短时间内提交相同的请求");
            }
            
            log.info("成功获取分布式锁: lockKey={}", lockKey);
            
            // 执行业务逻辑
            return supplier.get();
            
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            log.error("获取锁时被中断: lockKey={}", lockKey, e);
            throw new BusinessException(ErrorCode.SYSTEM_ERROR, "系统繁忙");
        } finally {
            // 释放锁（仅当当前线程持有锁时）
            if (acquired && lock.isHeldByCurrentThread()) {
                lock.unlock();
                log.info("释放分布式锁: lockKey={}", lockKey);
            }
        }
    }
}
```

**关键参数**：
- `waitTime = 0`：不等待，立即失败（快速失败原则）
- `leaseTime = 10`：10秒后自动释放（防止死锁）

**设计要点**：
1. **快速失败**：waitTime=0，重复提交立即返回错误
2. **防止死锁**：leaseTime自动过期
3. **安全释放**：检查isHeldByCurrentThread()
4. **异常处理**：InterruptedException恢复中断状态

## 6. 限流策略详解

### 6.1 为什么需要限流？

**场景**：
1. 恶意用户频繁调用接口
2. 爬虫批量抓取数据
3. 突发流量冲击

**后果**：
- 服务器资源耗尽
- 数据库连接池打满
- AI Token成本暴涨

### 6.2 限流策略设计

**双重限流**：
1. **频率限流**：每秒最多2次请求（防止恶意刷接口）
2. **每日限流**：普通用户3次/天，VIP用户50次/天（控制成本）

### 6.3 限流器实现

```java
@Service
public class RedisLimiterManager {
    @Resource
    private RedissonClient redissonClient;
    
    /**
     * 频率限流：每秒最多2次
     */
    public void doRateLimit(String key) {
        RRateLimiter rateLimiter = redissonClient.getRateLimiter(key);
        
        // 参数：限流类型、速率、时间间隔、时间单位
        rateLimiter.trySetRate(RateType.OVERALL, 2, 1, RateIntervalUnit.SECONDS);
        
        // 尝试获取令牌
        boolean canOp = rateLimiter.tryAcquire(1);
        if (!canOp) {
            throw new BusinessException(ErrorCode.TOO_MANY_REQUEST, 
                "请求过于频繁，请稍后再试");
        }
    }
    
    /**
     * 每日限流：普通用户3次，VIP用户50次
     */
    public void doDailyLimit(Long userId, String userRole) {
        String todayStr = getTodayStr(); // yyyyMMdd
        String dailyKey = "gen_chart_daily_" + userId + "_" + todayStr;
        RRateLimiter dailyLimiter = redissonClient.getRateLimiter(dailyKey);
        
        // 根据角色分配额度
        long dailyLimitCount = "vip".equals(userRole) || "admin".equals(userRole) 
            ? 50 : 3;
        
        // 初始化限流器
        if (!dailyLimiter.isExists()) {
            dailyLimiter.trySetRate(RateType.OVERALL, dailyLimitCount, 
                                    24, RateIntervalUnit.HOURS);
            dailyLimiter.expire(1, TimeUnit.DAYS);
        }
        
        // 尝试获取令牌
        if (!dailyLimiter.tryAcquire(1)) {
            String message = "vip".equals(userRole) 
                ? "今日次数已达上限 (50次)" 
                : "非会员每日仅限 3 次，请升级会员";
            throw new BusinessException(ErrorCode.TOO_MANY_REQUEST, message);
        }
    }
    
    /**
     * 查询剩余次数
     */
    public long getRemainingPermits(Long userId, String userRole) {
        String todayStr = getTodayStr();
        String dailyKey = "gen_chart_daily_" + userId + "_" + todayStr;
        RRateLimiter dailyLimiter = redissonClient.getRateLimiter(dailyKey);
        
        long dailyLimitCount = "vip".equals(userRole) || "admin".equals(userRole) 
            ? 50 : 3;
        
        if (!dailyLimiter.isExists()) {
            return dailyLimitCount;
        }
        
        return dailyLimiter.availablePermits();
    }
    
    private String getTodayStr() {
        SimpleDateFormat sdf = new SimpleDateFormat("yyyyMMdd");
        return sdf.format(new Date());
    }
}
```

### 6.4 限流回退机制

**问题**：先限流后加锁，如果锁获取失败，限流次数已被扣减

**解决方案**：限流回退

```java
/**
 * 回退用户的限流次数
 */
public void rollbackDailyLimit(Long userId, String userRole) {
    String todayStr = getTodayStr();
    String dailyKey = "gen_chart_daily_" + userId + "_" + todayStr;
    RRateLimiter dailyLimiter = redissonClient.getRateLimiter(dailyKey);
    
    // 如果限流器不存在，无需回退
    if (!dailyLimiter.isExists()) {
        log.warn("限流器不存在，无需回退: userId={}", userId);
        return;
    }
    
    // 计算总额度
    long dailyLimitCount = "vip".equals(userRole) || "admin".equals(userRole) 
        ? 50 : 3;
    
    // 获取当前剩余令牌数
    long availablePermits = dailyLimiter.availablePermits();
    
    // 如果已达上限，无需回退
    if (availablePermits >= dailyLimitCount) {
        log.info("限流次数已达上限，无需回退: userId={}", userId);
        return;
    }
    
    try {
        // 计算已使用次数
        long usedCount = dailyLimitCount - availablePermits;
        
        // 回退一次
        long newUsedCount = Math.max(0, usedCount - 1);
        
        // 删除旧限流器
        dailyLimiter.delete();
        
        // 重新创建限流器
        dailyLimiter = redissonClient.getRateLimiter(dailyKey);
        dailyLimiter.trySetRate(RateType.OVERALL, dailyLimitCount, 
                                24, RateIntervalUnit.HOURS);
        dailyLimiter.expire(1, TimeUnit.DAYS);
        
        // 预先消费已使用的令牌
        for (int i = 0; i < newUsedCount; i++) {
            dailyLimiter.tryAcquire(1);
        }
        
        log.info("成功回退限流次数: userId={}, 回退后可用次数={}", 
            userId, dailyLimiter.availablePermits());
        
    } catch (Exception e) {
        log.error("回退限流次数失败: userId={}", userId, e);
    }
}
```

**使用场景**：
1. 分布式锁获取失败（重复提交）
2. 文件读取失败
3. 参数校验失败（在限流之后）

### 6.5 限流算法对比

| 算法 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| 固定窗口 | 固定时间窗口计数 | 简单 | 临界问题 | 简单限流 |
| 滑动窗口 | 滑动时间窗口计数 | 平滑 | 内存占用大 | 精确限流 |
| 令牌桶 | 固定速率生成令牌 | 允许突发 | 实现复杂 | 流量整形 |
| 漏桶 | 固定速率处理请求 | 平滑输出 | 不允许突发 | 消息队列 |

**Redisson使用令牌桶算法**：
- 固定速率生成令牌
- 允许短时间突发（桶内有余量）
- 长期平均速率受限
