# 防重复提交与任务去重（分布式锁应用）实现文档

## 一、背景与需求

### 1.1 问题描述
目前的 `genChartByAiAsyncRabbitmq` 接口虽然有限流机制，但存在以下问题：
- 用户手抖连续点击多次，或在多个网页同时提交完全相同的文件和参数
- 后端会产生多条一样的昂贵 AI 分析任务
- 浪费 AI Token 成本和服务器资源

### 1.2 核心挑战
在使用分布式锁防重的同时，必须正确处理限流机制：
1. **先检查限流** → 检查用户是否还有剩余请求次数
2. **扣减次数** → 扣减一次请求次数
3. **分布式锁检查** → 验证是否为重复请求
4. **关键点**：如果分布式锁获取失败（重复提交），必须回退已扣减的请求次数

### 1.3 技术方案
使用 **Redisson 分布式锁** 实现请求去重，确保同一用户、同一内容的请求在短时间内只能处理一次。

### 2.2 关键流程说明

#### 流程 1：正常请求
```
用户提交 → 限流检查通过（扣减1次）→ 获取锁成功 → 处理请求 → 释放锁 → 返回成功
```

#### 流程 2：重复请求（需回退）
```
用户提交 → 限流检查通过（扣减1次）→ 获取锁失败 → 回退限流次数（+1次）→ 返回"重复提交"
```

#### 流程 3：其他异常（需回退）
```
用户提交 → 限流检查通过（扣减1次）→ 获取锁成功 → 业务异常 → 回退限流次数（+1次）→ 返回错误
```

## 三、核心代码实现

### 3.1 分布式锁服务

#### DistributedLockService 接口
```java
public interface DistributedLockService {
    /**
     * 尝试获取锁并执行业务逻辑
     * @param lockKey 锁的唯一标识
     * @param waitTime 等待获取锁的时间（秒）
     * @param leaseTime 锁的自动释放时间（秒）
     * @param supplier 需要执行的业务逻辑
     */
    <T> T executeWithLock(String lockKey, long waitTime, long leaseTime, 
                         Supplier<T> supplier) throws Exception;
}
```

#### 实现要点
- 使用 Redisson 的 `RLock`
- `tryLock(waitTime, leaseTime, TimeUnit)` 尝试获取锁
- 自动释放机制：`leaseTime` 后自动释放，防止死锁
- 仅当前线程持有锁时才释放：`lock.isHeldByCurrentThread()`

### 3.2 哈希工具类

```java
public class HashUtils {
    /**
     * 生成 MD5 哈希值
     */
    public static String md5(String data) {
        return DigestUtil.md5Hex(data);
    }
    
    /**
     * 生成请求的唯一标识
     * @param parts 组成唯一标识的各个部分
     */
    public static String generateRequestId(String... parts) {
        StringBuilder sb = new StringBuilder();
        for (String part : parts) {
            if (part != null) {
                sb.append(part).append("|");
            }
        }
        return md5(sb.toString());
    }
}
```

### 3.3 限流管理器扩展

#### 新增回退方法
```java
public void rollbackDailyLimit(Long userId, String userRole) {
    String dailyKey = "gen_chart_daily_" + userId + "_" + getTodayStr();
    RRateLimiter dailyLimiter = redissonClient.getRateLimiter(dailyKey);
    
    if (!dailyLimiter.isExists()) {
        return; // 限流器不存在，无需回退
    }
    
    long dailyLimitCount = "vip".equals(userRole) || "admin".equals(userRole) ? 50 : 3;
    long availablePermits = dailyLimiter.availablePermits();
    
    if (availablePermits >= dailyLimitCount) {
        return; // 已达上限，无需回退
    }
    
    // 回退操作：删除并重建限流器
    long usedCount = dailyLimitCount - availablePermits;
    long newUsedCount = Math.max(0, usedCount - 1);
    
    dailyLimiter.delete();
    dailyLimiter = redissonClient.getRateLimiter(dailyKey);
    dailyLimiter.trySetRate(RateType.OVERALL, dailyLimitCount, 24, RateIntervalUnit.HOURS);
    dailyLimiter.expire(1, TimeUnit.DAYS);
    
    // 预先消费已使用的令牌
    for (int i = 0; i < newUsedCount; i++) {
        dailyLimiter.tryAcquire(1);
    }
}
```

#### 回退逻辑说明
由于 Redisson 的 `RRateLimiter` 没有直接的"增加令牌"方法，我们采用以下策略：
1. 获取当前已使用的令牌数：`usedCount = total - available`
2. 计算回退后的已使用数：`newUsedCount = usedCount - 1`
3. 删除旧限流器
4. 重新创建限流器，设置总额度
5. 预先消费 `newUsedCount` 个令牌，恢复到回退后的状态

- 业务逻辑异常时回退

## 四、锁 Key 设计

### 4.1 锁 Key 格式
```
chart:gen:{userId}:{md5(fileContent + goal + chartType)}
```

### 4.2 设计原理
- **chart:gen**: 业务前缀，标识这是图表生成的锁
- **userId**: 用户ID，确保不同用户之间不互斥
- **md5(...)**: 请求内容的哈希值，确保相同内容会产生相同的锁

### 4.3 去重粒度
精准识别"同一个人提交的完全相同的内容"：
- 同一用户 ✓
- 相同文件内容 ✓
- 相同分析目标 ✓
- 相同图表类型 ✓

### 4.4 示例
```
用户A (ID=123) 提交文件file1.xlsx，目标"分析销售趋势"，类型"折线图"
→ 锁KEY: chart:gen:123:a1b2c3d4e5f6...

用户A 再次提交相同文件和参数（10秒内）
→ 锁KEY: chart:gen:123:a1b2c3d4e5f6... (相同！)
→ 获取锁失败 → 回退限流 → 返回"请勿重复提交"

用户B (ID=456) 提交相同文件和参数
→ 锁KEY: chart:gen:456:a1b2c3d4e5f6... (不同用户，可以处理)
```

## 五、限流回退机制详解

### 5.1 为什么需要回退？

**场景分析：**
```
1. 用户今天剩余次数：3次
2. 用户第一次提交 → 限流检查通过，扣减1次 → 剩余2次 → 获取锁成功 → 处理请求 ✓
3. 用户立即第二次提交（重复） → 限流检查通过，扣减1次 → 剩余1次 → 获取锁失败 ✗

问题：第二次请求虽然被拒绝了（重复提交），但次数被扣减了！
正确行为：第二次请求应该回退次数，恢复到2次。
```

### 5.2 回退触发条件

| 场景 | 是否回退 | 原因 |
|-----|---------|------|
| 限流检查未通过 | ❌ 不回退 | 没有扣减，无需回退 |
| 限流通过，获取锁失败 | ✅ 回退 | 扣减了但未处理，需要回退 |
| 限流通过，业务逻辑异常 | ✅ 回退 | 扣减了但未成功，需要回退 |
| 限流通过，处理成功 | ❌ 不回退 | 正常消费，不回退 |

### 5.3 回退实现挑战

Redisson 的 `RRateLimiter` 只支持"消费令牌"，不支持"归还令牌"。

**解决方案：**
1. 记录当前已使用次数：`usedCount = total - available`
2. 计算回退后次数：`newUsedCount = usedCount - 1`
3. 删除旧限流器
4. 重建限流器，重新消费 `newUsedCount` 个令牌

**代码流程：**
```
假设用户是普通用户，总额度3次，当前剩余1次（已使用2次）

1. usedCount = 3 - 1 = 2
2. newUsedCount = 2 - 1 = 1
3. 删除限流器
4. 重建限流器，设置总额度3次
5. 预先消费1次（tryAcquire）
6. 最终状态：剩余2次（已使用1次）
```

## 六、时间参数配置

### 6.1 分布式锁参数

| 参数 | 值 | 说明 |
|-----|---|------|
| waitTime | 0秒 | 不等待，立即失败。如果锁被占用，说明有相同请求正在处理 |
| leaseTime | 10秒 | 锁的最大持有时间。正常情况下业务逻辑会在1-2秒内完成，10秒足够防止意外死锁 |

### 6.2 为什么 waitTime = 0？

**设计考量：**
- 如果 `waitTime > 0`，第二个重复请求会等待锁释放后再执行
- 这违背了"去重"的初衷，我们希望立即拒绝重复请求
- `waitTime = 0` 确保重复请求立即失败，返回"请勿重复提交"

### 6.3 为什么 leaseTime = 10秒？

**设计考量：**
- **正常情况**：业务逻辑（数据清洗、保存数据库、发送MQ）通常在 1-2 秒完成
- **异常情况**：如果进程意外崩溃，锁会在 10 秒后自动释放，避免永久锁死
- **不能太短**：如果设置 3 秒，可能在正常处理时锁就释放了，导致重复请求通过
- **不能太长**：如果设置 60 秒，进程崩溃后用户需要等待很久才能重试

**权衡结果：10 秒**
- 正常请求：业务逻辑完成后主动释放锁（1-2秒）
- 异常情况：10秒后自动释放，用户可以重新提交

## 九、性能影响分析

### 9.1 额外开销

| 操作 | 耗时 | 说明 |
|-----|------|------|
| 计算文件MD5 | ~10ms | 对于1MB文件，MD5计算很快 |
| 获取分布式锁 | ~5ms | Redis网络往返，通常很快 |
| 释放分布式锁 | ~5ms | Redis网络往返 |
| 限流回退 | ~20ms | 删除并重建限流器，涉及多次Redis操作 |

**总额外开销：约20ms（正常情况）**

### 9.2 性能优化建议

1. **文件哈希优化**
   - 如果文件很大，考虑只计算前N个字节的哈希
   - 或者使用更快的哈希算法（如 xxHash）

2. **限流回退优化**
   - 回退操作较重（需要删除重建），但只在异常情况下触发
   - 正常情况下不会执行回退，对性能影响小

3. **锁超时设置**
   - 根据实际业务逻辑耗时调整 `leaseTime`
   - 监控实际锁持有时间，设置为 P99 耗时的 2-3 倍

## 十、故障场景与兜底

### 10.1 Redis 宕机

| 影响组件 | 影响 | 兜底方案 |
|---------|------|---------|
| 分布式锁 | 无法获取锁，所有请求失败 | 降级：去掉锁逻辑，允许重复（临时） |
| 限流器 | 无法限流，所有请求都会处理 | 熔断：返回"系统繁忙" |

**建议：**
- Redis 配置主从 + 哨兵，确保高可用
- 使用 Redisson 的红锁（RedLock）提高可靠性（多Redis实例）

### 10.2 锁永久未释放

**原因：**
- 进程崩溃时未正常释放锁
- 异常处理不当，finally 块未执行

**兜底：**
- `leaseTime` 参数确保锁最多持有 10 秒
- 定期扫描 Redis，清理超时的锁 KEY（可选）

### 10.3 限流回退失败

**原因：**
- Redis 临时不可用
- 并发操作导致状态不一致

**影响：**
- 用户的剩余次数少了 1 次（但请求未处理）

**兜底：**
- 记录回退失败日志，人工补偿
- 为 VIP 用户提供"次数恢复"功能

## 十一、最佳实践建议

### 11.1 开发规范

1. **锁 KEY 命名规范**
   - 使用业务前缀：`chart:gen:`、`order:create:` 等
   - 包含用户标识：避免不同用户互斥
   - 包含业务唯一标识：精准去重

2. **异常处理规范**
   - 所有可能失败的点都要考虑限流回退
   - 使用 try-catch-finally 确保锁释放
   - 区分业务异常和系统异常

3. **日志规范**
   - 获取锁成功/失败都要记录
   - 回退操作必须记录
   - 包含关键上下文：userId、lockKey、请求参数

### 11.2 运维建议

1. **监控告警**
   - 重复提交率 > 10%：可能有异常流量
   - 锁超时率 > 5%：业务逻辑可能过慢
   - 回退失败率 > 1%：Redis 可能有问题

2. **容量规划**
   - 估算每日请求量，确保 Redis 容量充足
   - 锁 KEY 会自动过期（10秒），不会占用太多内存

3. **灰度发布**
   - 先在小流量环境测试
   - 观察重复提交率、响应时间等指标
   - 逐步放开到全量

## 十二、总结

### 12.1 核心要点
1. **分布式锁去重**：使用 Redisson 实现，`waitTime=0` 立即拒绝重复请求
2. **限流回退机制**：扣减后获取锁失败，必须回退次数
3. **锁 KEY 设计**：`chart:gen:userId:md5(content)`，精准识别相同请求
4. **自动释放**：`leaseTime=10秒`，防止死锁

### 12.2 适用场景
- ✅ 用户提交表单、文件上传等操作
- ✅ 需要消耗昂贵资源的操作（AI、短信、支付等）
- ✅ 需要精准去重的场景（相同内容只处理一次）
- ❌ 高频读取操作（没必要加锁）
- ❌ 对性能要求极高的场景（锁会增加延迟）

### 12.3 扩展方向

   - 扩展：可以只根据 fileContent 去重（全局去重）

   - 如果检测到重复请求，可以返回上一次的结果（如果已完成）
   - 需要额外的状态查询逻辑

   - 使用 Redisson 的 RedLock 算法
