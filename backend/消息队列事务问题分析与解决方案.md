# 消息队列事务问题分析与解决方案

## 问题描述

在执行 `/gen/async/rabbitmq` 和 `/edit/rabbitmq` 接口时，MQ日志显示"非事务环境"，导致数据库操作和MQ消息发送不在同一个事务中。

## 问题原因

1. **Controller层不在事务中**：Controller方法默认不在Spring事务管理中
2. **分布式锁方法无事务**：`DistributedLockService.executeWithLock()` 方法没有 `@Transactional` 注解
3. **Lambda表达式不在事务中**：即使Service方法有事务，lambda表达式中的代码也不在事务管理范围内

### 原来的代码流程

```
Controller (无事务)
  └─> DistributedLockService.executeWithLock() (无@Transactional)
      └─> Lambda表达式 (无事务)
          ├─> chartService.createChart() (可能有独立事务)
          ├─> chartMapper.createChartTable() (可能有独立事务)
          ├─> chartMapper.insertChartData() (可能有独立事务)
          └─> biMessageProducer.sendMessage() (无事务环境，立即发送)
```

## 不在同一事务中的潜在问题

### 1. 数据不一致风险

**场景1：数据库操作成功，MQ消息发送失败**
```
1. 数据库操作成功提交（chart表创建成功，数据表创建成功）
2. MQ消息发送失败（网络问题、RabbitMQ宕机等）
3. 结果：数据库中已有数据，但MQ队列中没有消息
4. 影响：消费者无法处理该图表，图表状态永远为"wait"
```

**场景2：MQ消息发送成功，数据库操作失败回滚**
```
1. MQ消息发送成功（消息已进入队列）
2. 数据库操作失败并回滚（创建数据表失败等）
3. 结果：MQ队列中有消息，但数据库中没有对应的数据
4. 影响：消费者处理消息时找不到对应的图表数据，导致业务异常
```

### 2. 消息丢失风险

**场景3：数据库提交后，应用崩溃，MQ消息未发送**
```
1. 数据库操作成功提交
2. 应用在发送MQ消息前崩溃
3. 结果：数据已持久化，但消息未发送
4. 影响：需要人工介入或通过定时任务补偿
```

### 3. 重复处理风险

**场景4：数据库操作成功，MQ消息重复发送**
```
1. 数据库操作成功
2. MQ消息发送成功
3. 由于网络问题，生产者未收到确认，重试发送
4. 结果：同一条消息被发送多次
5. 影响：消费者可能重复处理（需要幂等性保证）
```

## 解决方案

### 1. 使用事务同步机制（TransactionSynchronization）

在 `BiMessageProducer.sendMessage()` 方法中，使用 `TransactionSynchronizationManager` 检测事务环境：

```java
if (TransactionSynchronizationManager.isActualTransactionActive()) {
    // 在事务中，注册事务后钩子
    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                // 事务提交成功后，发送MQ消息
                doSendMessage(chartId, isVip);
            }
        }
    );
} else {
    // 非事务环境，直接发送
    doSendMessage(chartId, isVip);
}
```

### 2. 创建事务服务层

创建 `ChartTransactionService`，将所有数据库操作和MQ消息发送放在同一个 `@Transactional` 方法中：

```java
@Service
public class ChartTransactionServiceImpl implements ChartTransactionService {
    
    @Transactional(rollbackFor = Exception.class)
    public Long createChartWithTransaction(Chart chart, List<String> headers, 
                                          List<List<Object>> dataRows, boolean isVip) {
        // 1. 创建图表
        chartService.createChart(chart);
        // 2. 创建数据表
        chartMapper.createChartTable(tableName, headers);
        // 3. 插入数据
        chartMapper.insertChartData(tableName, headers, dataRows);
        // 4. 发送MQ消息（事务提交后发送）
        biMessageProducer.sendMessage(String.valueOf(chartId), isVip);
        return chartId;
    }
}
```

### 3. Controller中调用事务服务

在Controller的lambda表达式中调用事务服务方法：

```java
distributedLockService.executeWithLock(lockKey, waitTime, leaseTime, () -> {
    // 调用事务服务方法（所有操作在同一事务中）
    long chartId = chartTransactionService.createChartWithTransaction(
        chart, headers, dataRows, isVip
    );
    // 缓存删除等操作在事务外执行
    evictChartCache(null, userId);
    return response;
});
```

## 修复后的代码流程

```
Controller (无事务)
  └─> DistributedLockService.executeWithLock() (无@Transactional)
      └─> Lambda表达式 (无事务)
          └─> ChartTransactionService.createChartWithTransaction() (@Transactional)
              ├─> chartService.createChart() (同一事务)
              ├─> chartMapper.createChartTable() (同一事务)
              ├─> chartMapper.insertChartData() (同一事务)
              └─> biMessageProducer.sendMessage() (事务后钩子，提交后发送)
                  └─> TransactionSynchronizationManager.registerSynchronization()
                      └─> afterCommit() { doSendMessage() }
```

## 优势

1. **原子性保证**：数据库操作和MQ消息发送在同一事务中，要么全部成功，要么全部回滚
2. **消息防丢失**：使用事务后钩子，确保事务提交后才发送消息
3. **数据一致性**：避免了数据已提交但消息未发送的情况
4. **可维护性**：事务逻辑集中在Service层，Controller层更简洁

## 注意事项

1. **缓存操作**：缓存删除等操作应该在事务提交后执行，避免影响事务性能
2. **分布式锁**：分布式锁的获取和释放应该在事务外，避免锁持有时间过长
3. **异常处理**：事务回滚时，MQ消息不会发送（符合预期）
4. **性能考虑**：事务后钩子机制会稍微增加延迟，但保证了数据一致性

## 总结

通过创建事务服务层并使用Spring的事务同步机制，我们确保了数据库操作和MQ消息发送的原子性，避免了数据不一致和消息丢失的问题。这是处理分布式事务的常用模式，既保证了数据一致性，又不会过度影响系统性能。
